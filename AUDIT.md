## 3. Исправленные дефекты

### A1. Ложная ошибка «Недостаточно места для портов блока» (высокая)

**Симптом.** Проект ниже документированного предела в 500 блоков не строился:
480 операторных устройств, подключённых к одному сетевому шкафу
(`blocksPerRow=8`, всего 481 блок), давали `ValueError` и HTTP 422. При
`blocksPerRow=12` отказ начинался примерно с 485 целей. Через CLI ошибка
возникала и на 560 целях, хотя README обещает работоспособность до 559.

**Причина.** `PortRegistry.free_pos` перебирал не более 512 позиций. В длинном
межколоночном зазоре число занятых X-координат может быть больше 512: функция
возвращала `None` с обеих сторон, `seat()` бросал исключение, хотя место было.
Ограничение было замаскировано под «физический предел»: граница 559/560 на
самом деле определялась тем же счётчиком 512, а не шириной грани.

**Исправление.** Бюджет поиска привязан к числу занятых записей
(`len(self.occupied) + 512`): каждый шаг гарантированно перепрыгивает хотя бы
одну запись, поэтому поиск не может зациклиться и не обрывается раньше времени
(`structural_scheme/routing.py`). Чтобы обещанный предел оставался
детерминированным, он сделан **явным**: `MAX_PORTS_PER_EDGE = 559` в
`constants.py` и проверка в `layout()` перед посадкой портов. Поведение для
560+ портов не изменилось (та же понятная ошибка и тот же HTTP 422), но теперь
она не зависит от эвристики поиска. Проекты на 481 блок и 480 целей строятся,
`layoutProblems() == []`, в предупреждениях есть «Шаг портов 0.34 px…».

**Регрессии.** `test_registry_searches_past_512_occupied_slots`,
`test_many_targets_to_one_net_cabinet_are_laid_out`,
`test_registry_reports_exhausted_search_instead_of_merging_lines`; прежние
`test_huge_fan_in_fails_with_clear_error` и
`test_dense_layout_time_is_bounded` проходят без ослабления.

### A2. HTTP 500 на большие целые числа (средняя)

**Симптом.** `{"racks":[{"servers": 999…(400 цифр)}]}` — валидный JSON — давал
500 на `/api/normalize`, `/api/preview` и всех экспортах; CLI падал трейсбеком.

**Причина.** Проверка типа вызывала `math.isfinite(int)`, а преобразование
целого, не помещающегося в double, бросает `OverflowError`
(`normalize.py`, `_pick`). Такой же незакрытый путь был в `countWarnings` и
`blockLines`.

**Исправление.** Хелпер `_finite()` превращает `OverflowError` в «не число»;
неподходящее значение заменяется default, как и любой другой неверный тип.
`countWarnings`/`blockLines` ловят `OverflowError` для прямых вызовов с
произвольным состоянием.

**Регрессии.** `test_huge_integers_fall_back_to_defaults_instead_of_crashing`,
`test_hostile_json_values_do_not_return_500`.

### A3. Невалидный XML и 500 на управляющие символы (средняя)

**Симптом.**

- `title` с `\u0000` или `\u0001`: `/api/export/svg` отвечает 200, но файл не
  парсится (`not well-formed`); PNG — 422; Draw.io тоже невалиден.
- Одиночный суррогат `\ud800` в любой строке: `/api/normalize` отвечает 500
  (`PydanticSerializationError`), потому что Python-строка не кодируется в UTF-8.

**Причина.** `normalizeState` принимал любые строки без проверки на символы,
недопустимые в XML 1.0. `ElementTree` сериализует их без ошибки, поэтому дефект
не ловился тестами на валидность.

**Исправление.** `clean_text()` в `text_utils.py` удаляет C0-управляющие
(кроме `\t`, `\n`, `\r`), одиночные суррогаты и `U+FFFE/U+FFFF`; применяется
ко всем строкам при нормализации (включая ID). SVG/Draw.io снова всегда
валидный XML, `/api/normalize` не падает. Поведение задокументировано в README
и AGENTS.md.

**Регрессии.** `test_xml_invalid_characters_are_stripped_during_normalization`,
`test_hostile_json_values_do_not_return_500`.

### A4. Неполный публичный API пакета (средняя)

**Симптом.** `from structural_scheme import normalizeState` → `ImportError`,
хотя README прямо обещает сохранение API оригинала (`normalizeState`,
`parseState`, `serializeState`, `makeResolvers`, фабрики элементов), а AGENTS.md
называет `structural_scheme/__init__.py` публичным API. Работал только импорт
из `structural_scheme.scheme_core`.

**Исправление.** В корень пакета и `__all__` добавлены
`normalizeState`/`normalize_state` и `newOpItem`, `newRack`, `newNetCab`,
`newAutoCab`. Регрессия: `test_public_api_exposes_documented_core_functions`.

## 5. Открытые замечания и рекомендации

### B1. Примечания и заголовок не ограничены шириной листа (средняя)

`notesText` рисуется построчно без переноса и обрезки: строка в 640 знаков даёт
ширину текста ≈3644 px при листе 1054 px, хвост обрезается в SVG/PNG. Заголовок
в 10 повторений даёт ≈2335 px. `layoutProblems` проверяет только выход
примечаний за нижнюю границу, поэтому проблема не видна ни валидатору, ни
пользователю. Рекомендация: переносить строки примечаний по `textWidth` и/или
обрезать заголовок с предупреждением в `model['warnings']`; добавить проверку
ширины в валидатор. Не исправлялось в аудите, чтобы не менять геометрию
существующих проектов без согласования.

### B2. Ограничения на входе API (низкая)

Нет лимита размера тела запроса и числа строк примечаний: 100 МБ JSON будет
прочитан в память (лимит 500 блоков проверяется уже после разбора). Нет
`Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`.
Рекомендация: middleware с предельным размером тела (например, 5 МБ) и
базовые заголовки. XSS-риск низкий: серверный SVG экранируется, а клиент
дополнительно вычищает `script`/`on*`/`javascript:` в `renderSvg`.

### B3. Сеть по умолчанию (низкая, осознанно)

`python -m structural_scheme` слушает `0.0.0.0` без аутентификации (нужно для
preview в Arena) и печатает предупреждение. README честно указывает
`--host 127.0.0.1`. Для публичной сети приложение не предназначено; стоит
сохранить это предупреждение и не убирать возможность явного `--host`.

### B4. CI (низкая)

- нет `permissions: contents: read` — токен по умолчанию может быть шире нужного;
- нет `concurrency` (лишние прогоны на серию push) и `timeout-minutes`;
- матрица 3.11/3.13 без 3.12 (заявлено `>=3.11`);
- покрытие не публикуется артефактом/в отчёт, только проверяется порог.

### B5. Документация и мелочи (низкая)

- `for me.md` фиксирует «46 тестов, покрытие 97.8%, PR #2, ветка
  `arena/756f2206…`», хотя сейчас 55 тестов и 100%; это исторический отчёт, но
  читателю легко принять его за текущее состояние. Стоит обновить вручную
  после реального прогона, а не переписывать числа автоматически.
- `port` из переменной окружения `PORT` при мусоре даёт трейсбек вместо
  понятного сообщения `argparse` (`PORT=abc python -m structural_scheme`).
- `generate.py` печатает предупреждения модели только после успешного экспорта:
  при ошибке экспорта они теряются.
- `countWarnings` при прямом вызове с огромным int печатает в предупреждение
  полный `repr` числа (после A2 через `buildScheme` такое значение уже не
  проходит).
- `scheme_core.__all__` экспортирует приватные `_band`, `_net`, `_new`, `_pick`
  (историческая совместимость с JS; не мешает, но расширяет контракт).
- `reference/` содержит устаревшие README/AGENTS исходного JS-проекта (Node,
  `npm`, сборка `index.html`). Это помечено как исторический материал, но
  поиск по репозиторию может ввести в заблуждение; можно добавить в
  `reference/README.md` первую строку «исторические материалы, не инструкции».

## 6. Сильные стороны

- Единая модель: геометрия считается один раз, SVG/Draw.io/растры только
  рисуют её; проверено отсутствие мутаций и совпадение точек.
- Точное интервальное раскрашивание подтверждено свойством
  «число слотов = максимальная глубина» на Hypothesis.
- Охранные тесты производительности и фиксированной точки зазора действительно
  ловят возврат квадратичных алгоритмов.
- Нет CDN, Node, облака и сетевых зависимостей во время работы; браузерные
  тесты блокируют внешние запросы и падают на `pageerror`.
- Понятные пользовательские ошибки и предупреждения (обрезка подписей, шаг
  портов, некорректные числа), одинаковые в UI, CLI и API.
- Хорошая гигиена: `py.typed`, wheel с `static/`, `.gitignore` для кэшей и
  результатов экспорта, русские комментарии с объяснением причин решений.
